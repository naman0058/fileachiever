# Digital Diary with Password Protection

A full-stack **MERN** personal journal and productivity workspace. Users write rich diary entries, manage tasks and reminders, store encrypted secret notes and personal documents, read admin-published PDF books, and customize appearance—all behind account security, optional app lock, and role-separated admin CMS. The app uses **local MongoDB**, **local file storage**, and **no third-party APIs** for core functionality.

---

## Project Overview

### What it does

Digital Diary is a privacy-oriented daily journal and life organizer. End users capture thoughts with a rich-text editor, organize entries by category, pin favorites, attach media, and export selected entries. Productivity modules (tasks, reminders, checklists, calendar) sit alongside a password-protected vault for secret notes and structured storage for identity documents (e.g. Aadhaar/PAN-style fields). A curated **books library** serves in-app PDF reading. Administrators operate a separate CMS to manage users, platform content, branding, feature flags, and aggregate reports—**without access to users’ private diary bodies, secret notes, or personal documents**.

### Purpose

Provide a self-hosted, client-ready digital diary product suitable for demos, coursework, or deployment on a private server, with realistic Indian demo data and clear separation between user privacy and admin operations.

### Main users / roles

| Role | Description |
|------|-------------|
| **Visitor** | Browses the public marketing/landing site; may register or log in if registration is enabled. |
| **User** | Authenticated account owner; full access to `/app/*` workspace for their own data only. |
| **Administrator** | Separate login at `/admin/login`; manages platform settings and shared content, not user private journals. |

There are **no** vendor, staff, teacher, or other multi-tenant roles in this codebase—only **User** and **Admin**.

### Core workflow

1. Visitor lands on `/`, reviews features and branding, then **Register** or **Login**.
2. After login, optional **app lock** (PIN/pattern) may gate access to `/app`.
3. User writes diary entries, uses dashboard shortcuts, calendar, search (⌘/Ctrl+K), and productivity tools.
4. User adjusts **Profile**, **Security**, and **Appearance** under Account routes.
5. Admin maintains categories, books, quotes, themes, support tickets, and global settings via `/admin`.

### Major capabilities (summary)

- Rich diary CRUD with search, filters, sort, pagination, favorites, pins, attachments, note backgrounds.
- Secret notes with per-note lock (password/PIN/pattern); content hidden until unlock.
- Personal documents (typed forms + optional file upload) with masked display in lists.
- Tasks (pending/completed), reminders (types + completion), checklists with item toggles.
- Calendar views for diary entries, tasks, and reminders.
- Books library with PDF reader (PDF.js), favorites, recently viewed.
- Daily motivational quotes (admin-managed).
- User backup/restore (JSON) for diary, tasks, reminders, checklists, preferences.
- Bulk diary export (PDF or TXT per entry).
- Admin CMS: users, content, brand, contact, settings, reports.
- Feature flags to hide registration, books, quotes, themes, attachments, etc.

## User Roles / Panels

### Public / landing side

- **Routes:** `/` (marketing landing), `/login`, `/register`, `/forgot-password`.
- **Behavior:** Loads brand name, logo, favicon, contact info, and feature flags from the public brand API. Registration respects admin **registrationEnabled** flag.
- **No authenticated workspace** on these routes.

### User panel (`/app/*`)

- Wrapped in **JWT auth** (`PrivateRoute`) and optional **AppLockGate** (PIN/pattern when enabled).
- **AppShell:** sidebar navigation, breadcrumbs, global search, theme toggle, mobile bottom nav, create menu.
- All data scoped to the logged-in user on the server.

### Admin panel (`/admin/*`)

- **Login:** `/admin/login` → stores `adminToken` in `localStorage`.
- **AdminRoute:** requires admin JWT (`ADMIN_JWT_SECRET`).
- **AdminShell:** grouped CMS navigation, dashboards, tables, forms.
- **Privacy model:** Admin APIs do not expose diary entry content, secret note bodies, or personal document fields for end users.

## Authentication & Security

### Registration

- Required: name, email, phone, password, confirm password, security question (from fixed list), security answer.
- Password policy: minimum 8 characters, upper, lower, digit, special character (`server/src/utils/passwordPolicy.js`).
- Can be disabled globally via admin **registrationEnabled**.

### Login / logout

- **User:** `POST /api/users/login` → JWT stored client-side; `Authorization: Bearer` on protected routes.
- **Logout:** client clears token (user session).
- **Admin:** `POST /api/admin/login` → `adminToken` in `localStorage`; separate JWT secret.

### Password handling

- Passwords hashed with bcrypt (cost 12) on save.
- Security answers hashed (normalized lowercase).
- Change password via authenticated profile endpoints with policy validation.

### Forgot / reset password

- Request step with email + security question/answer.
- Reset with new password meeting policy.

### Role-based access

- User middleware: valid user JWT + status not `blocked`.
- Admin middleware: valid admin JWT with `role: admin`.

### Account status & locking

- **Admin-blocked** users (`status: blocked`) cannot use the API.
- **Failed login lockout:** after `maxFailedLoginAttempts` (default 5), account locked for `lockDurationMinutes` (default 15)—configurable in admin settings.

### App lock (user device session)

- Optional PIN or pattern before entering `/app` (Security page).
- Verified via dedicated API; stored hashed server-side.

### Admin privacy boundary

- No admin routes to read user diary content, secret notes, or personal documents.
- Reports aggregate users/support/books metadata only.

## How to Run the Project

From a fresh clone on Windows, macOS, or Linux:

### 1. Open the project

```bash
cd "Digital Diary with Password Protection"
```

### 2. Install dependencies

```bash
cd server
npm install

cd ../client
npm install
```

### 3. Configure environment

```bash
cd ../server
copy .env.example .env
```

On Unix:

```bash
cp .env.example .env
```

Edit `server/.env` (see [Environment Configuration](#environment-configuration)).

### 4. Start MongoDB

Ensure MongoDB is running and reachable at the URI in `.env` (default `mongodb://127.0.0.1:27017/digital_diary`). The database is created automatically on first connection.

### 5. Seed sample data (development)

```bash
cd server
npm run seed
```

For a full refresh of demo users only:

```bash
npm run seed:reset
```

### 6. Start the backend

```bash
cd server
npm run dev
```

Server listens on **port 5000** by default.

### 7. Start the frontend

In a second terminal:

```bash
cd client
npm run dev
```

Vite serves the app on **port 5173** and proxies `/api` and `/uploads` to the backend.

### 8. Open the application

| URL | Purpose |
|-----|---------|
| http://localhost:5173 | Landing page |
| http://localhost:5173/login | User login |
| http://localhost:5173/register | User registration |
| http://localhost:5173/app | User workspace (after login) |
| http://localhost:5173/admin/login | Admin login |
| http://localhost:5173/admin | Admin CMS (after admin login) |
| http://localhost:5000/api/health | API health check |

### Production build (frontend only)

```bash
cd client
npm run build
npm run preview
```

Serve `client/dist` behind a static host or reverse proxy; set `CLIENT_URL` and API base URL to match your deployment. The Express server does not serve the React build by default—you typically deploy API and static frontend separately or extend the server.

## File Uploads / Storage

All files are stored **locally** under `server/uploads/`:

| Subfolder | Used for |
|-----------|----------|
| `attachments/` | Diary entry attachments |
| `profiles/` | User profile images |
| `documents/` | Personal document files |
| `books/` | Book PDFs and cover images |
| `themes/` | App theme background images |
| `note-backgrounds/` | Admin note background assets |
| `brand/` | Logo, favicon, auth page backgrounds |

**Diary attachments**

- Default max size: **10 MB** per file (`maxFileUploadSizeMB` in AppSettings).
- Default allowed MIME types: `image/jpeg`, `image/png`, `image/webp`, `video/mp4`, `application/pdf`.
- Up to **10 files** per upload request on an entry.

**Other uploads**

- Profile, documents, admin assets: Multer limit **50 MB** per file in upload helper (admin book PDFs/covers use `fieldsUpload`).

Files are exposed at `/uploads/<subdir>/<filename>`.

## Important Project Restrictions

- **No third-party APIs** required for core features (auth, storage, content are self-contained).
- **Local MongoDB** required; no built-in SQLite fallback.
- **Local disk** for uploads—ensure writable `server/uploads` and backup strategy in production.
- **Internet:** optional for local dev; needed only for npm install and font packages (bundled at build).
- **Admin cannot** audit private user journal or vault content by design.
- **Backup/restore** does not move secret notes, documents, or attachment binaries.
- **`express-rate-limit`** is a dependency but not applied in `index.js` unless you add middleware yourself.

## Troubleshooting

| Issue | Likely cause | Fix |
|-------|----------------|-----|
| `ECONNREFUSED` / MongoDB errors | MongoDB not running | Start `mongod` or fix `MONGODB_URI` |
| `EADDRINUSE :::5000` | Port 5000 in use | Stop other process or change `PORT` in `.env` |
| CORS errors from browser | Wrong frontend origin | Set `CLIENT_URL` to exact Vite/production URL |
| Login works in Postman but not UI | Proxy misconfigured | Use Vite dev on 5173 or configure API base URL in client |
| Attachment rejected | MIME not allowed | Admin → Settings → allowed attachment types |
| Empty books library | Feature disabled or no active books | Admin settings + Books module; run seed |
| `Cannot POST /api/auth/login` | Wrong path | User login is **`POST /api/users/login`** |
| PowerShell `&&` fails | Shell syntax | Use `;` between commands or run steps separately |
| Seed skips demo data | Users already exist | Run `npm run seed:reset` for demo refresh |
| Theme text hard to read | Light shell + dark mode mismatch | Use Appearance save or SunMoon toggle after theme update (fixed in app CSS—rebuild client if needed) |
